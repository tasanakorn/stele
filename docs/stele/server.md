# Server Internals

## Entry Points

`main.rs` contains two `fn main()` implementations selected at compile time by feature flags:

- **`#[cfg(feature = "desktop")] fn main()`** — Parses config, initialises the DB, loads the saved bind address from the settings file (`config.toml`), spawns the server on a background `std::thread` with its own tokio runtime, then runs the winit/tray event loop on the main thread.
- **`#[cfg(not(feature = "desktop"))] #[tokio::main] async fn main()`** — Parses config, initialises the DB, spawns a Ctrl+C handler that cancels the shutdown token, then calls `run_server()` directly on the main async thread.

Both paths share the `run_server()` function for all server logic.

## Server Startup Flow

`run_server()` performs the following steps:

1. Creates a `StreamableHttpService` using a `SteleServer::new(pool)` factory closure so each MCP session gets its own `SteleServer` instance.
2. Uses `LocalSessionManager` for MCP session management (in-process, no external broker).
3. Builds an axum `Router` with:
   - The MCP service nested at the configured `mcp_path` (default `/mcp`).
   - The REST API router nested at `/api`.
4. Binds a `TcpListener` to the configured address.
5. Serves with axum's graceful shutdown, driven by a `CancellationToken`.
6. Enters a rebind loop: `tokio::select!` waits for one of three signals — shutdown (process exit), rebind (address changed), or server-exit (listener error). On rebind the child `CancellationToken` is cancelled (stopping the current listener), a new listener is bound to the new address, and the loop continues. On shutdown the parent token is cancelled and the function returns.

## MCP Layer

Implemented in `server.rs`:

- **`SteleServer`** struct holds a `DbPool` and a `ToolRouter<Self>` (generated by the macro).
- **`#[tool_router] impl SteleServer`** — defines all tool methods. The macro collects them into a router stored on the struct.
- **`#[tool_handler] impl ServerHandler for SteleServer`** — auto-implements `call_tool`, `list_tools`, and `get_tool` by delegating to the router.
- Each tool method: acquires the DB mutex, calls a function in `db.rs`, and returns a JSON string. rmcp wraps the string in a `Content::text` response automatically.
- Tool parameter structs must derive `schemars::JsonSchema` from schemars v1 (not v0.8 — rmcp requires v1).
- Lenient deserialization is applied via `serde_helpers.rs`. Claude Code sometimes encodes arrays as JSON strings; the helpers transparently handle both forms so tools receive typed `Vec<String>` regardless of wire format.

## REST Layer

Implemented in `api.rs`:

- Router mounted at `/api` with `CorsLayer::permissive()` for browser access.
- Request and response types are private structs defined in `api.rs` — they are not shared with the MCP layer.
- Handlers use `State<DbPool>` and call the same `db.rs` functions as the MCP tools, so behaviour is identical across both interfaces.
- Scope parameters arrive as comma-separated strings in query params (e.g. `?scope=team-a,team-b`) rather than JSON arrays as used in MCP.

## Settings Dialog

Desktop-only feature implemented in `settings.rs`:

- An egui dialog that lets the user choose the bind address: localhost, all interfaces, or a custom IP/port.
- Settings are persisted to `config.toml` in the same directory as the DB file.
- The dialog is launched as a subprocess from the tray menu via `--settings --db <path>`. Running it as a subprocess keeps the GUI on a separate process so it does not interfere with the main server thread.
- While the subprocess is alive the tray module polls `config.toml` every 500 ms. When a change is detected the tray signals the `BindState` notifier, which triggers a live rebind in `run_server()`.

## Auth Middleware

Implemented in `auth.rs`, used by both desktop and headless builds:

- `AuthState` holds an `RwLock<Option<String>>` key that can be updated at runtime without restarting the server. Desktop tray actions (Generate / Copy / Clear) write to it via `blocking_set`; the async middleware reads it via `.read().await`.
- Key resolution precedence: CLI flag `--auth-key` > env var `STELE_AUTH_KEY` > `auth_key` in `config.toml` > open (no auth).
- The `nest_service` call for the MCP endpoint requires the middleware to be applied **before** wrapping — `tower::ServiceBuilder` handles this separately from the top-level `.layer()` call, which covers all REST routes. Both use the same `Arc<AuthState>` so they stay in sync.
- Keys are 32 random bytes encoded as URL-safe base64 (no padding), 43 characters long.
- Comparison is constant-time to resist timing attacks.

## Tray Module

Implemented in `tray.rs` (desktop feature only):

- Implements winit's `ApplicationHandler` trait to receive OS-level window and menu events.
- Menu items: a status label showing the current bind address, an "Auth Key" submenu, Settings, Open Dashboard (opens the web UI in the default browser), and Quit.
- "Auth Key" submenu contains: Generate Key (creates and copies a new key), Copy Key, Clear Key. Status row shows "Auth Key: set" or "Auth Key: none". Changes are persisted to `config.toml` immediately and take effect for the live server without a restart.
- Polls `config.toml` every 500 ms while the settings subprocess is alive. Updates the tray status label when the address changes and signals the server rebind notifier.
- Quit menu item cancels the parent `CancellationToken`, which propagates shutdown to the background server thread.

## Stylos Session Lifecycle

Since v0.17.0 stele-server can embed a zenoh peer via the `stylos` crates (see [PRD-022](../prd/prd-022-stylos-in-stele-server.md)).

- **Feature gating.** Both `desktop` and `headless` include the `stylos` cargo feature by default. An opt-out build is `cargo build -p stele-server --no-default-features --features headless-minimal`.
- **Module.** `src/stylos_module.rs` owns the `Arc<zenoh::Session>`, the heartbeat task, the info queryable task, and the shutdown routine.
- **Instance derivation.** Explicit override (config / `STELE_STYLOS_INSTANCE`) > normalized hostname (lowercased, non-`[a-z0-9-]` mapped to `-`, trimmed, 32-char cap) > `stele-<first-8-of-zid>` fallback.
- **Heartbeat.** Every 5 s `put(b"alive")` on `stylos/<realm>/stele/<instance>/heartbeat` with `Encoding::APPLICATION_OCTET_STREAM`, `CongestionControl::Drop`.
- **Info queryable.** Replies on `stylos/<realm>/stele/<instance>/info` with a JSON blob (`Encoding::APPLICATION_JSON`) containing zid, mode, realm, instance, version, stylos_version, listen_endpoints (currently empty — see limitation below), started_at.
- **Session lives above the rebind loop.** `STELE_BIND` rebinds restart only the axum listener; the zenoh session (and its ZID) survive untouched.
- **Shutdown order.** Rebind loop exits → heartbeat and queryable tasks are aborted and awaited → `session.close().await`. Tied to the same `CancellationToken` as the axum listener.
- **Known limitations.**
  - `listen_endpoints` is always reported as `[]` in both `/api/v1/health.stylos` and the info-queryable payload; zenoh 1.9 exposes no stable public listener enumeration API.
  - When the cargo `stylos` feature is on but `[stylos].enabled = false`, the session is skipped entirely and `/api/v1/health.stylos` reports `{ "enabled": false }`.

## Graceful Shutdown

Shutdown is coordinated via `CancellationToken` from the `tokio-util` crate:

- A parent token represents the process lifetime.
- A child token is created per rebind cycle and represents the current server listener.
- **Desktop mode** — tray Quit menu item calls `cancel()` on the parent token.
- **Headless mode** — a spawned task listens for `tokio::signal::ctrl_c()` and then calls `cancel()` on the parent token.
- Cancelling the child token stops only the current server (triggering a rebind). Cancelling the parent token stops the rebind loop and exits the process.
